# 二维码入口与 NFC 补卡工程说明

更新日期：2026-10-18。本文是二维码跨端流程的主文档；历史设计、实施与发布证据分别保留在原计划和[验证记录](VERIFICATION.md)。

## 1. 范围与状态

二维码不是另建一套录音系统，而是同一个云端展签身份的另一种入口。适用场景包括当天实体卡不足，以及参观者手机无法读取 NFC、但可以扫码打开网页和录音。二维码不能解决手机没有摄像头、浏览器不能录音或网络不可用的问题。

| 能力 | 当前状态 | 边界 |
| --- | --- | --- |
| staff/运营网页签发二维码 | 已上线，PR #21/#23 | 每次创建一个独立云端展签，不创建写卡任务 |
| 扫码录音、原子绑定、播放 | 已上线 | 复用现有访客 token 路由、私有存储和播放授权 |
| 二维码页列表与旧码回看 | 已上线，PR #26 | 仅本浏览器标签页的 sessionStorage，不是跨设备历史 |
| 后台/APP查询共用录音数据 | 已有通用查询基础 | 不等于已有二维码专用检索、标识或补卡操作 |
| 录音后在 Android APP 中补写实体卡 | **待开发，本文为 Proposed 设计** | 当前不能按本节规划直接操作生产卡 |
| 双手机与实体芯片完整验收 | 待现场验证 | 云端合成测试不能代替手机麦克风与实体 NFC 验收 |

本次文档整理不新增 API、数据库迁移、APK 或生产操作。补卡的具体数据模型和接口须先冻结，再开发调用端；本文候选字段不是已可调用的 API。

## 2. 同一个身份，两种入口

```text
staff 网页创建 tagId + 稳定 visitorUrl
                  |
                  v
二维码 -> 访客扫码 -> 录音绑定该 tagId -> 云端录音
                  |
                  | 后续补卡（待开发）
                  v
Android 找到同一 tagId -> 空白芯片写入同一 visitorUrl -> 读回并同步
                  |
                  v
二维码或 NFC 均打开原 tagId、原录音
```

- 补卡不是将音频移动到另一个展签，不新建第二条录音，也不改变 `recordings.tag_id`、token 或原 visitorUrl。
- 原二维码始终有效；补卡后的芯片只是多一个访问原记录的载体。参观者手机不支持 NFC 时，仍然使用原二维码。
- 常规 NFC 仍是先写唯一 URL、再由参观者碰卡录音；二维码后补卡是显式例外，不取代原流程。
- 一条云端展签身份最多一段有效录音；不提供“一枚已分配身份的卡与另一条录音合并”的快捷操作。

## 3. 已实现流程与当前缺口

### 网页签发与历史

工作人员从 `#/staff` 进入 `#/staff/qr`，运营后台保留 `#/admin/qr`。独立子页面只有签发/显示/回看二维码流程，不需要选择审核署名。服务端验证既有会话，通过 `createQrEntry` 原子创建 `entry_channel='qr'` 的展签身份，用 requestKey 保证不确定结果重试不多创建。

二维码编码服务端返回的 `https://voice.heisei.space/#/t/<opaque-token>`。参观者沿用现有录音、地点/主题选择、提交、收听流程；音频不在二维码或芯片中。

签发后新条目自动选中，可点旧条目回看；历史按用户保存在当前标签页的 sessionStorage，刷新后可恢复，退出/认证失败时清理历史及当前/待重试请求 key。它不是云端签发台账，不跨手机同步，也不能保证浏览器清理或关闭后可找回。

签发响应中的编号是创建时的库存号；录音提交后云端会产生正式编号。当前本地签发历史不会持续刷新正式编号。跨端查找应使用服务端 `tagId` 定位，并允许用库存号或正式编号搜索，不能把显示号当唯一身份。

### 后台与 Android

二维码记录与 NFC 记录共用 `tags`、`recordings`、编号历史及私有音频。通用管理列表可返回二维码记录；现有后台可查询/试听。staff 查询 DTO 不提供 token 或写卡任务，不应为补卡把完整运营数据塞进 staff 列表。

Android 当前通过 `admin-api` 查询卡片、试听和领取写卡任务。其卡片解析尚未消费 `entryChannel`，没有专用二维码补卡筛选或操作。二维码记录没有 provisioning job，因此不能通过现有单张“写回原网址”或连续写新卡完成补卡。`renderCards` 对没有 job 的记录使用 `pending` 回退文案；这不等于有待写实体任务，补卡开发须同时更正该状态呈现。通用列表出现录音不代表已与实体卡联动。

## 4. 方案比较与推荐

| 方案 | 影响 | 结论 |
| --- | --- | --- |
| 为原 QR 身份显式补写同一 URL | 原录音、二维码、编号与审核结果不变；需专用准备/核验流程 | **推荐，Proposed** |
| 新建普通 NFC 身份，再迁移录音 | 涉及旧链接、编号、转写、地点、审计和并发上传归属 | 不采用 |
| 把 QR 记录直接放进普通空卡池 | 连续写卡可能领取已有参与者的录音身份 | 不采用 |

## 5. 推荐补卡工作流（待开发）

第一版限定“已成功录音的 QR 记录 + 实体空白可写芯片”，逐条确认，不批量补写、不覆盖已有 NDEF 的芯片。

1. 工作人员用现有 Android 运营登录进入“二维码补卡”流程；不新增角色，也不把共享 staff 网页账号自动升级为写卡账号。
2. 按库存号/正式编号及录音日期查询云端记录，显示 QR 来源、是否已录音、是否已补卡、录音时间和编号；必要时试听。日期筛选含义必须明确，录音日与签发日不能混用。
3. 核对参与者出示的二维码或提交结果编号。首版可用编号搜索；相机扫码/网页跳转 APP 仅作后续便捷入口，不是首版依赖。无凭证时不能仅凭“最新一条”自动选人。
4. APP 先读实体芯片，确认是空白、可写、容量足够且没有其他展览 URL。已有内容、只读、未知状态一律停止，不自动清空、不删除原云端记录。
5. 向服务端显式申请该 QR 身份的补卡任务/租约，校验身份、录音和展签版本；展示目标编号并确认。不能调用普通 `prepareWrite` 代替。
6. APP 将服务端固定的完整 visitorUrl 写入已确认的同一枚芯片，再读回比较完整 URL。换芯片、内容变化、切后台、账号变化或租约失效，均需重新核查。
7. 读回一致后提交核验报告。服务端接受前标为“芯片已写，等待同步”，不得显示完整流程成功，也不得把相同任务自动写到另一枚芯片。
8. 服务端确认后显示“已补卡”；保留原二维码。用另一台手机碰卡/扫码，确认访问同一条录音。

后续若要支持预写卡替换、补第二张、丢卡重补或未录音 QR 先补卡，应作为明确的新需求设计，不能借首版补卡隐式开放。

## 6. 数据与接口边界（Proposed，未冻结）

- `entry_channel='qr'` 保留为签发来源，不应仅改成 `nfc` 来绕过写卡池隔离。未来展示应区分“二维码签发，未补卡”和“二维码签发，已补卡”，不能继续把全部 QR 来源一律称为“仅二维码”。
- 录音绑定状态与实体补卡状态独立。补卡全过程不得重置/解绑录音；待补卡、准备中、物理结果未知、已写待同步、已核验分别展示，不与 `unbound/bound/disabled` 混用。
- 需要服务端持久化补卡记录，包括目标 tagId、目标录音/展签版本、任务身份、操作者、设备、租约、核验状态/时间和审计。不能只靠网页历史或 APP 本地布尔值。
- 设计优先考虑独立补卡任务实体，复用现有 NFC 读写与报告恢复逻辑；不要未经审查往旧 provisioning_jobs 增加多条记录或直接复用普通任务。既有 DTO/查询可能依赖一展签一任务，须逐处核对。
- 新增的逻辑能力包括：QR 及补卡状态查询、精确读取单条身份、幂等准备补卡、核验报告、取消/恢复核查。字段名、分页筛选、错误码、协议版本与表结构在实现前统一写入 API 契约并配套测试；当前 API 不承诺支持这些操作。
- 普通 `jobs/nextJob/prepareWrite/leaseJob/provision` 的现有语义不扩大；QR 补卡只通过显式专用路径，旧 APP 不得误领任务。查询筛选必须在服务端分页前完成。
- 准备操作按记录加锁、检查版本并提供持久幂等 key；同一记录同一时刻只允许一个有效补卡任务，重复报告不产生第二次分配。首版默认不允许已核验记录再次申请新卡。
- NFC UID 只能作当前触碰防换卡的临时线索，不作为公开身份或跨端查找键。云端分配约束不能防止第三方复制普通 NDEF URL，不宣称硬件防克隆。

## 7. 失败恢复与安全

数据库事务与物理芯片写入不是同一事务。超时、断连、APP 被杀、云端版本变化都可能发生在已经写卡之后；不能用数据库回滚宣称撤销了实体写入。

- 写入前版本不符、录音不存在/已重置、展签禁用/删除或已有有效补卡任务：拒绝准备或执行，不更换目标记录绕过。
- 开始物理写入前持久化任务、固定 URL、账号/项目范围和“不确定”标记；写后云端断网保留原核验报告，只重试同步。
- 写入中断/读回失败：先重新读取同一芯片核对，不自动把同一 URL 写入新芯片；不能安全确认时转人工处理。
- 写入期间并发重置/删除/禁用：服务端在最终报告时再次校验；若物理已写但云端拒绝，则保留异常记录并人工核查，不能标记成功或静默建新身份。
- 退出/换账号、切后台须停止 NFC；待同步记录按项目/账号隔离。取消任务不撤销已发生的物理写入；不确定任务不能自动释放给另一枚芯片。
- 访客 URL 不是写卡授权。补卡沿用 Android 既有运营认证与服务端校验，不把 service_role 放入 APP，也不让 staff 二维码子页增加写卡、重置或覆盖功能。
- 审计保留任务、目标身份、操作者、设备、时间和结果；不记音频正文、完整 token/URL、租约 token 或私有播放链接。

## 8. 开发与验收顺序

1. 负责人确认本方案范围，冻结来源/补卡状态模型、专用 API、协议兼容和恢复规则；将候选接口转为正式契约。
2. 后端实现持久任务、授权、原子租约/幂等、审计和精确查询；测试并发准备、重复报告、重置竞争、旧 APP 写卡池隔离。
3. 管理网页补充来源与补卡状态摘要；QR 签发子页面继续只签发/显示/回看，不承担实体写卡。
4. Android 增加 QR 来源/补卡状态解析、定位确认、先读空白卡、专用补写和中断恢复；回归普通连续写卡、单张原卡恢复和账号切换。
5. 隔离数据全链路通过后，按既有备份/迁移/发布流程上线；旧 APP 与新 API 的兼容边界须在发版前验证。

必须验收：两位参与者 QR 不串号；二维码录音后经 APP 补卡，原二维码与芯片打开同一 tagId/recordingId；完整 URL 写后读回一致；音频、正式编号、地点、转写和审核结果不变；双 APP 并发同记录只有一个有效任务；断网/杀进程不重复配卡；已有内容/只读/容量不足拒绝；最终报告与重置/禁用竞争不伪报成功；匿名/staff 越权被拒绝；旧连续模式仍只领普通空卡。

实体测试记录 Android/参观者手机型号与 OS、浏览器、芯片型号/容量和网络。现有[验证记录](VERIFICATION.md)只证明已上线 QR 基础链路，不证明本补卡规划已实现或验收。
