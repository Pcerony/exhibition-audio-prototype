# 后台拼装板定位与转写状态设计

## 目标

运营者查看一条录音时，可以知道参观者选择的位置大致落在实体地图的哪一块拼装板上，并据此寻找对应 NFC 卡。73 块拼装板编号是唯一的定位口径，不使用预览页中的原方格网格代替。预览说明将板块编号定义为 A-H 从北向南、每行从西向东；C 行为 C1-C10，其余各行 1-9。编号和实体位置以[打印说明](https://pcerony.github.io/fukuoka-city-model-preview/README.md)为准。

后台同时让运营者能在记录列表中识别转写进度。转写正文继续由现有的单条转写窗口读取和审核，不进入列表 DTO。

## 当前系统约束

- 参观者的音频上传及 `public-upload-claim` 绑定是首要流程；地点随录音绑定保存。该流程的成功不能依赖拼装板计算。
- claim 可按地点是否存在写入简单的初始 assignment 状态（待计算或不适用），但不得在 claim 事务中做点位计算、调用外部地图服务或等待 assignment 请求。
- 手动落针地点持久保存用户确认的经纬度；搜索地点持久保存 `placeId`，不长期保存 Google 返回的坐标、地址或名称。
- NFC token、录音绑定关系、音频私有存储和授权规则保持不变。
- 目前运营列表不返回转写状态或正文；运营者可以按录音 ID 单独读取转写。
- 地图预览提供的是打印拼装板方案。它的板块轮廓必须另行整理成可供应用使用的、版本化地理几何数据；仅凭屏幕截图或打印盘序 CSV 不足以进行坐标匹配。

## 参观者提交与自动计算

1. 参观者完成现有录音上传和绑定。地点与录音按既有契约一同保存；claim 成功即确认录音已提交。
2. **只有 claim 成功后**才开始拼装板归属计算。计算与保存使用独立、可重试的后续操作，不属于音频和地点 claim 的成功条件。
3. 计算以参观者当次明确选择的点和版本化的 73 块地理轮廓做点在多边形内判断。搜索地点坐标仅在当前交互中使用；长期保留的自动结果为板块编号及地图版本，不新增 Places 坐标持久化。
4. 自动计算或后续保存失败时，录音及地点仍保持已提交。参观者看到的提交结果仍是成功；后台将该记录显示为待定位或需核对，运营者可重新计算或手动指定板块。
5. 计算必须幂等。迟到的自动结果不得覆盖运营者已作出的手动修正。无地点、图外地点或落在无法明确归属边界上的点，不伪造板块编号。

当前实现由参观者在claim请求中短暂携带当前选择点`mapPoint`；服务端先完成录音/地点claim，再在同一HTTP处理流程内以版本化几何分类，并单独调用最小assignment RPC，只提交板块编号、状态和地图版本。`mapPoint`不得进入SQL、日志或响应，Place ID仍是长期地点记录。分类/RPC失败不改变claim成功结果；若后续改成客户端独立请求，仍须保持“claim先成功、计算独立可失败”的外部行为，并提供运营端补正入口。

## 后台工作流

- 记录列表每行显示板块编号，例如 `C6`，并区分自动分配、手动修正、待定位/需核对和未选地点。
- 选择记录时，73 块地图总览高亮对应板块；选择板块时，列表筛选到该板块的记录，便于在图上反查卡片。
- 运营者可在地图上选择实际放置卡片的板块并保存修正。保存时记录旧值、新值、操作者和时间；修改后的来源标记为手动，自动计算不得覆盖。
- 转写状态在同一列表以文字状态和筛选项呈现：未同意、待处理、处理中、草稿待审核、已发布、失败。列表只返回同意标记、状态和发布标记，不返回转写正文；点“文字转写”仍打开既有窗口。
- 搜索、批次、录音状态和分页行为保持现状；筛选板块或转写状态不得改变现有卡片权限或公开播放规则。

## 数据与接口

- 新增板块归属元数据：`pieceCode` 可空；`assignmentState` 为 `not_applicable`、`pending`、`assigned`、`needs_review` 或 `outside_map`；`assignmentSource` 为 `automatic`、`manual` 或空；另有 `mapVersion`、更新时间。地点缺失与自动计算未成功必须能在 UI 中区分。手动修改需能关联运营者并写入审计记录。
- 参观者自动 assignment 使用独立的最小权限操作，只能为当前成功 claim 的录音提交合法板块编号；不得修改音频、地点、token、绑定状态或其他管理字段。重复请求幂等。
- 运营端手动修正通过认证 Admin API 完成，使用版本检查避免覆盖并发修改，并写入审计。
- Admin `list` 返回板块归属摘要及转写状态摘要，但不含 transcript text 或 Places 返回的坐标、地址、名称，也不泄露内部错误详情。既有手动 pin 坐标的读取行为维持 API 契约，不因本功能额外扩展。正文仍通过现有 `getTranscription` 按需读取。
- API 契约、调用方、Edge Function 授权测试和管理 UI 类型必须一起更新。服务端密钥不得进入网页或请求响应。

## 地图数据与准确性

- 生成可审查的 73 个唯一板块轮廓，统一到明确的坐标参考系，并为几何数据设定 `mapVersion`。
- 自动归属必须覆盖所有已定义板块，验证边界无未解释的缝隙或重叠；边界容差应显式定义。边界不明确时返回需核对，不静默选错块。
- 用地图上可核验的已知地点逐块抽样，比对自动结果和实体拼装板标号。未完成地理配准和抽样验证前，不在生产记录中宣称归属准确。
- 当前 Google 地点存储约束维持不变；发布前复核坐标的使用和派生板块编号持久化是否符合当前 [Google Maps Platform Places 政策](https://developers.google.com/maps/documentation/places/web-service/policies)。Place ID 可保存，但其他 Places 内容的缓存/存储受限制。

## 失败与恢复

- 音频上传失败或 claim 失败：沿用现有错误流程，不创建已提交记录或板块 assignment。
- claim 成功、自动几何计算或保存失败：保留录音与地点；assignment 保持待计算，后台显示待定位。运营者可在地图上手动选择实际板块；仅当可可靠取得原始选择点时才提供重新计算。
- assignment 请求超时或重复：不改变录音状态；安全重试，不能覆盖手动结果。
- 无地点：显示“未选地点”。地点在地图覆盖区外：显示“图外”。无法从 `placeId` 当前选择点得到坐标：显示“需核对”，不阻塞提交。
- 手动修正失败：保留旧板块值，提示运营者重试；写入审计与更新必须原子化。
- 转写任务状态异常不影响录音和板块定位；转写正文只在已授权的运营端窗口中读取。

## 验收

- 自动计算发生在 claim 成功之后；模拟计算异常、网络超时及非法板块编号时，音频和地点仍可在后台读取，参观者提交仍显示成功。
- 测试 pin 与搜索地点、所有 73 个编号、图外点、板块边界、无地点、重复 assignment、超时重试以及地图版本变更。
- 手动修正需要运营者认证，审计旧值/新值/操作者/时间；迟到的自动请求不得回滚手动结果。
- 列表显示转写状态并可筛选，但列表响应和 CSV 均不包含转写正文；无同意录音不会被标为可转写。
- 运行 `npm test -- --run`、`npm run build`、`GITHUB_PAGES=true npm run build`，以及适用的 migration dry-run、RLS/Edge Function 授权、assignment 幂等和失败隔离测试。
- 生产部署前由集成负责人审核迁移、备份和地理配准结果；不以本地几何测试代替真实地点抽查。
